# Teleprompt · 0.1.40

## 准备讲稿

手机打开 **STUDY → Teleprompt**，输入／粘贴讲稿，或点 **Import TXT** 从手机选择 `.txt`。导入后可编辑；Save 保存，Start follow 和 On glasses 也会先保存当前草稿。重复保存相同内容不重置位置；修改内容会回到开头并暂停跟读。

- 最多 60,000 字符，TXT 最多 512 KB，超限直接提示。
- 支持 UTF-8、带 BOM 的 UTF-16 LE／BE、GB18030。
- 展开 **Title / language / voice engine** 修改标题、语言、麦克风灵敏度、连接方式和 OpenAI 转写模型。
- Live preview 查看眼镜位置；Restart 回到开头。讲稿本地保存，导入和保存本身不上传文件。

## 眼镜操作

从 **Study → Teleprompt** 或手机 On glasses 打开。只有明确开始跟读才收音。

| 操作 | 效果 |
| --- | --- |
| 单击 | 开始／暂停语音跟读，等待 300ms 区分双击 |
| 长按 | 开始／暂停跟读 |
| 上／下滑 | 手动移动两行并重设语音锚点 |
| 双击 | 返回 Study，停止收音、关闭实时连接、取消在途请求 |

固定标题、七行原生正文、底部状态和页码；`>` 固定在第二行，是视觉阅读焦点。上方最多一行已读内容，下面五行未读内容；讲稿开头的上方和末尾的下方允许留空。已读行亮度较低，焦点行亮度最高，未读内容保持可读。

## 0.1.40：柔和阅读交接

识别位置继续及时更新，显示位置通过独立交接器跟随：

1. 下一行先从亮度 3 预亮至 4，焦点旧行从 4 稍降至 3，让眼睛先看到即将进入焦点的内容；`>` 位置保持不动。
2. 正文只推进一行，将预亮的同一句文字移入第二行阅读焦点，亮度仍为 4；旧行移到上方，亮度先为 2。
3. 旧行再降至亮度 1，保留下方五行未读内容。标题和图标不参与交接。

迟到的一段识别即使指向几行以后，也按这个过程逐行经过；只保存最新目标，不给每个 ASR 更新排动画队列。没有新语音时只会完成已确认结果的交接，不按固定计时无限滚动。过渡会有意增加一点显示跟随时间，极端落后时仍要花时间逐行追到已识别的位置。

手机展开 **Title / language / voice engine → Reading transition**：

| 选项 | 交接节奏 |
| --- | --- |
| Soft handoff（默认） | 每行目标约 320ms，下一行预亮、焦点交接、旧行渐暗 |
| Calm handoff | 每行目标约 480ms，给眼睛更长的交接时间 |
| Immediate | 直接显示最新识别行，保留固定焦点和已读／未读亮度层次 |

时间是应用设定的最小显示节奏，真实速度还受眼镜原生文字请求完成时间影响；逐帧等待完成后才推进，不发送重叠动画帧。切换即生效并保存，不重启语音或额外调用识别 API。手动滑动从实际可见的行移动两行，立即取消未完成的旧交接，再重设语音锚点；Restart／更改讲稿同样取消旧过渡。

这是一种**原生文字的柔和交接**，不是逐像素平移。SDK 0.0.16 的文字更新只开放内容和亮度，位置／尺寸仅能在重建布局时改变；没有文档化的像素滚动／动画控制。本版用七个文字容器和一个标题图像，保持原生字体，不为过渡重建页面或发送整页位图。

手机 Live preview 显示交接中的行和亮度，Reading 为显示行，recognized 为识别已到达的行，两者在追赶期间可能暂时不同。离开页面、断连或课表提醒时取消正在等待的动画帧；回到页面后可继续向最近确认位置交接。

## 0.1.39：连续词位置追踪

0.1.37 先录约 3.2 秒再串行等待两次 API。0.1.38 接入实时转写，但本地定位仍有 4 个英文词／8 个汉字门槛。0.1.39 把短增量跟踪放在这个门槛之前：

1. **持续实时转写**：Auto 在转写 URL 为 OpenAI 官方域名时选择 Realtime，默认 `gpt-live-transcribe`、`delay: minimal`。16kHz 眼镜 PCM 在手机上连续重采样为 API 所需的 24kHz，音频发送缓冲约 40ms（实际还取决于宿主交付的音频帧长度）；模型的增量文字到达即可参与定位，不等完整句子上传完。约 220ms 停顿后提交当前音频段。GPT Live 连续朗读最多约 6 秒才切段，避免每 2 秒切断上下文；增量定位一直运行，不等这 6 秒。需要提交后才能转写的备用 Realtime 模型约 0.9 秒一段。短词最低有效语音长度降至约 120ms。连接建立后明确发送 session.update，确认配置生效后才开麦。
2. **本地快速定位**：保存已确认的词位置，处理 ASR 增量时替换当前片段，跨音频段保留最近字词，不将重复 partial 当成新词。已定位后，一个能确定位置的新词可以直接更新当前行，跨行不再要求先读出下一行多个词。不确定时才使用较长短语恢复定位；重复词、数字、可能尚未说完的英文前缀会等待更多证据，避免跳到后面的相同词。
3. **AI 语义补充**：本地无法可靠定位且有足够信息时请求现有聊天模型识别同义改写；partial 也可请求，不必等最终句子。增量语义判断节流约 900ms，仍可能消耗更多聊天请求。独立于转写运行，最多一个请求在途、一个最新请求等待；不会阻塞后续音频。语义请求仍检查严格 JSON、置信度与实际语音证据。语义 API 出错时保留本地跟读并显示原因，重新开始跟读后可重试。
4. **兼容模式**：HTTP 每段缩短至约 1.2 秒，或约 220ms 停顿后提交，转写返回后同样先本地定位。只保留最新等待音频，不堆积长队列。OpenAI 默认用 `gpt-4o-mini-transcribe`，自定义服务沿用 Setup → Voice 的模型。

麦克风继续按能量门限过滤静音，屏蔽宿主标记为 Other 的说话人；Unknown 不作为可靠身份判断。不会向 ASR 提供讲稿内容，避免静音误识别成预期讲稿。语音很短、重复、模糊或无关时可保持原位置；同义改写仍受聊天请求耗时影响。

手机展开 **Speech / timing** 可看到最近转写、实际选择的模型、单个 PCM 音频帧时长、partial／final 数量和本地匹配耗时。Realtime 的 `first text` 是音频段开始发送至首次收到可用文字的观测时间，包含实际说话时长；HTTP 的 `request → text` 是开始请求至返回文字，二者口径不同，不能直接当作模型内部耗时比较。它们均不是逐词结束至显示的测量。诊断更新不单独触发眼镜刷新，也不保存转写历史。

**能否保证每个词结束后 1 秒内准确定位？目前不能。** 代码已取消已定位场景下必须攒够多词的等待，持续使用 GPT Live / minimal delay；但云端返回增量的时机、网络、宿主音频帧和眼镜文字传输均有延迟，重复词或同义改写也需要上下文。OpenAI 官方没有为该模式承诺固定的毫秒延迟。若 Heard 已及时出字但行不动，重点看匹配；若 Heard 本身迟到且没有 partial，重点看转写／网络／音频交付。

## 模型与连接

| 设置 | 行为 |
| --- | --- |
| Auto / OpenAI Realtime | 官方 OpenAI 转写 URL 用 Realtime，其他 URL 用 HTTP |
| OpenAI Realtime | 明确使用官方 OpenAI 实时转写；使用 Voice Key，留空则 Chat Key |
| HTTP compatibility | 使用现有文件转写 URL 和 relay；官方 URL 使用下方 OpenAI speech model，GPT Live 映射为 GPT-4o mini |
| GPT Live / minimal delay | 默认连续实时模型，增量结果可在提交前到达 |
| GPT-4o mini / GPT-4o transcribe | 备用转写模型，实时模式下通常需要提交音频段后才返回文字 |
| Whisper / compatibility | 可兼容旧模型，但不提供同样的实时增量效果 |

明确设置中文或 English 可减少识别歧义。模型、语言或连接方式更改时暂停跟读，点 Start follow 保存设置并生效。AI assistant 原来的 Voice 模型不受此处 OpenAI 模型选项影响。聊天模型须支持 Chat Completions 严格结构化 JSON（例如已有 `gpt-4o-mini`）。

**不需要额外服务商 Key**。需要现有 OpenAI 项目的模型调用权限、API 余额和可用网络；Realtime 及语义判断分别消耗 API 配额。若没有 GPT Live 权限可选 GPT-4o mini；WebSocket 不通可选 HTTP。连接失败时明确暂停，不静默回退并把旧模式显示成实时。

启用 Realtime 时通过 `POST /v1/realtime/client_secrets` 获取 60 秒有效的短期凭证来建立连接。长期 Key 沿用既有私人 HUD 的设置／HTTPS 请求方式，不放在 WebSocket URL 或子协议里；短期凭证仅在内存中使用。使用旧版自部署 relay 时必须更新 relay，以开放固定 `/openai/realtime/client_secrets` 路由；开发版重启 Vite 即可。**音频 WebSocket 直接连接 OpenAI，HTTP relay 不会代传 WebSocket**，所以手机仍需能访问 `wss://api.openai.com`。否则可选 HTTP compatibility，继续使用旧 relay 的 `/openai/audio/transcriptions`。

官方参考：[实时转写](https://developers.openai.com/api/docs/guides/realtime-transcription)、[短期凭证](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create)、[WebSocket 认证](https://developers.openai.com/api/docs/guides/voice-websockets?voice-api=realtime)、[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=chat)。

## 自动与手动同时使用

手动滑动立即改变窗口并重设语音锚点，清空语音缓存、取消在途请求。Realtime 会建立新的会话，杜绝旧会话迟到的增量结果覆盖手动位置；重连期间可以继续手动阅读。自动结果还检查阅读修订号、音频段顺序和过期时间。自动只前进；向上回看后可重新朗读。同向 100ms 内重复手势合并。

## 暂停与退出

暂停、编辑草稿、切换语音引擎、离开页面、退出插件或断连时停止跟读、关闭实时连接并请求关闭麦克风。与 AI 聊天共用串行麦克风控制队列；转写连接错误暂停收音，避免持续无效请求。课表提醒覆盖页面时暂停，关闭提醒恢复后按原跟读意图重新连接。插件被系统终止后不会自动开启麦克风。

讲稿保存本地；音频与识别文本仅短暂留在内存。跟读会将音频传给转写服务，并按需将转写与附近少量讲稿传给聊天服务，不发起联网搜索，不加入聊天记录。

本版只做 TypeScript 与生产构建，没有使用用户 Key 发起付费 API 调用，没有运行自动化测试。实际端到端延迟及噪声、同义改写定位仍需安装后确认，未承诺固定毫秒数。
