# 渲染性能对比与优化

调研日期：2026-10-17。当前应用使用 Even Hub SDK 0.0.16。

## 为什么会逐角显示

原来的全屏详情统一使用四张 288×144 图片拼成 576×288 画面。文字虽然已经原生化，边框、标题图标和信息分隔线仍走整屏图片路径。每次布局切换都会清空图片缓存，因此需要逐张发送四张图片，四角会先后出现。PNG 编码已经并行，但图片发送会等待上一张的桥接返回；编码并行无法消除这四次发送等待。

图片经宿主解码和内部 LZ4 压缩后传输。PNG 文件大小、图像像素面积、桥接返回耗时和最终眼镜显示帧率是不同指标。不能根据浏览器的 60 Hz 定时器断言真机达到 60 FPS，也不能仅凭压缩 PNG 很小断言传输很快。

## 参考实现

用户提供的商店信息为 Stack（codrin）和 Minesweeper（Jam）。按名称与作者检索后，尚未找到可以核实的公开源码，无法确认这两个安装版本采用的具体渲染方式、刷新次数或吞吐量。

后来找到了用户举例的 [Taiwan Bus Tracker / G2BusTracker 源码](https://github.com/jamie950315/G2BusTracker/blob/main/src/main.ts)。`showHome` 仅创建一个原生标题和一个原生列表，菜单图标使用字符，选中框由原生列表处理；到站卡片与常用路线路由页也主要采用原生文字容器。它并非把整页转换成图片再同时传输。用户确认接受字符图标并优先响应速度后，当前 HUD 主界面也改用原生字符图标。

找到并检查了同平台的两个公开游戏：

- [Paddle 的 renderer.ts](https://github.com/nickustinov/paddle-even-g2/blob/main/g2/renderer.ts)：游戏运行时把球、球拍、棋盘表示为 Unicode 文字，通过 `textContainerUpgrade` 更新；分数仅在变化时更新。多个独立文字请求一起发起。`pushInFlight` 防止帧请求积压。
- [Paddle 的 game loop](https://github.com/nickustinov/paddle-even-g2/blob/main/g2/app.ts)：每轮等待发送后才进行下一轮。README 的约 80 ms 是循环目标，不是对我们设备的实测帧率。
- [Blocks](https://github.com/nickustinov/blocks-even-g2)：运行中的棋盘同样使用原生文字网格，游戏结束前不重建页面。图片主要用于启动和结束画面。
- 本地官方 SDK 的 `README.md`、`dist/index.d.ts`：支持原生文字亮度 0–4、原生边框；单个图片容器的尺寸为宽 20–288、高 20–144；公开图片更新接口没有整页图片原子提交参数。

这些实现可以证明原生文字、差量更新和限制在途刷新请求是可借鉴的方法；不能据此断言 Stack 或 Minesweeper 的内部实现与它们相同。这里借鉴方法，未引入第三方游戏代码。

## 当前采用的改进

| 场景 | 原来 | 现在 |
| --- | --- | --- |
| 进入 AI / 待办详情 | 四张 288×144 图片承载边框和图标 | 原生边框、原生文字，仅一张 20×20 标题图标 |
| 进入 Information | 四张全屏拼图 | 原生外框和文字，标题图标与精确 1px 横线共用两张稀疏图片 |
| AI 回复 / 聊天滑动 | 原生文字更新 | 仍只更新变化的原生文字，不发送图片 |
| 主界面切换选项 | 图标和栏目名称分开更新 | 四个原图标集中在一张 20×114 图片中；名称和 `<` / `-` 选中标记一起置于原生文字容器，四项亮度一致，切换时只更新变化的文字，不发送图片 |
| 主界面栏目分隔线 | 单独的 262×20 图片 | 原生文字在页面创建时显示；同一列图片显示四个菜单图标 |
| 快速滑动 / 多数据源更新 | 每次调用都排队 | 一个刷新任务循环读取最新状态，合并中间请求 |
| 图片发送过程中出现新请求 | 发送完旧画面剩余图块 | 在途图片完成后取消旧画面未发送的图块 |
| 天气页 | 整屏文字、图表、分隔线与地图合在四块位图 | 文字与外框原生显示；地图、符号、范围图、风向图标、月相与精确 1px 分隔线使用图片 |

AI / 待办进入页面时需要传输的图片像素面积从 165,888 降至 400，减少约 99.76%。0.1.23 的 Information 为 31,304 像素，天气详情为 70,015 像素，环境页为 57,550 像素；新增面积用于可靠承载精确 1px 分割线，文字不进入图片。这是图片像素面积的结构变化，不是相同幅度的耗时或 FPS 提升保证。原生文字和边框指令仍有传输成本。

录音状态需要改变聊天边框亮度时，重新建立轻量原生布局并发送一个小图标。平常收到回复或滑动聊天不重建布局。

0.1.14 将四个原先绘制的图标重新用于首页。为符合 4 个图片容器的 SDK 上限，时钟、天气、电量和一列 20×114 图标共用四个图片容器。四个栏目名称和选择标记由原生文字绘制；所有标签固定亮度 4，选中显示 `<`，未选中显示 `-`。0.1.16 将四行标记放在一个独立原生文字列中，共用同一横坐标，不再使用标题后的空格定位。模拟器截图中四行标记和下方横线的最右侧像素均为 x=522。首页共有八个文字容器和四个图片容器，符合 SDK 上限。滑动时变更标记列和概要，无需重发图标或栏目名称。

0.1.17 将 Information 页的分隔线改为原生文字，去掉两张横线图片。天气页按地图、10 日预报、天气详情、环境信息切换原生布局。标题、页码、天气数据和横竖分隔线均由原生文字容器显示；地图视图保留一张地图图像，预报页保留两列天气符号，环境页保留月相图，所有页面保留天气标题图标。地图标签随地图数据绘制在地图图像内。

0.1.18 恢复原始视觉结构：预报恢复两列五行，星期、低温、高温分别使用固定坐标的原生文字列，保留低温较暗的层次；按 27px 原生行高居中排列，天气符号和温度范围条保留为图像；天气详情恢复三列两行，环境恢复两列两行。连续横竖线与 Information 横线均使用 1px 高或宽的原生边框，不再用多行字符拼竖线。详情页每列的两张卡片共享一个原生文字容器，按 27px 原生行高排版，下排起点为 y=164；环境卡片使用各自容器，维持原来的 y=56/157。标题与原生外框共享一个容器，另用原生小圆点表示分页，所有页面保持在 8 个文字和 4 个图片容器以内。预报图片分为四个仅承载符号/图表的区域，包含标题图标，数据文字不进入图片。

主界面初始化包括像素时钟、天气、电池和图标列四块图片。0.1.13 起分隔横线改成原生文字容器；0.1.14 将四个独立图标合并为一张窄图列。菜单文字、选择标记和横线随页面容器创建；时钟、天气、电池与图标列仍逐张传输，无法承诺整页同步呈现。

0.1.19 针对真机点击 Weather 后一直停在首页、双击才能返回操作的反馈，修正了天气原生容器名称超限。官方 [Display & UI System](https://hub.evenrealities.com/docs/build/display) 限定 `containerName` 最多 16 字符；原地图页的 `weather-map-title` 为 17 字符，`weather-map-status` 为 18 字符，另外三页也有超长名称。本地 SDK 校验与之前的模拟器运行未拦截这些名称。这是确定存在的协议违规，与反馈相符；尚无真机桥接日志证明它是唯一原因。当前改为短名称，并在所有 HUD 布局提交前检查长度。天气布局、文字或图片调用报告失败时，串行渲染任务会恢复首页状态和布局，手机显示具体错误；不会对未完成的图片调用超时后并发重试。排版与图像尺寸保持不变，需要安装 0.1.19 在眼镜上确认结果。

可选构建参数 `VITE_HOME_MENU_RENDERER=bitmap` 保留原手绘图标。图标、文字与横线合成为一张 262×114 菜单图片，同一选项的图标和文字由同一张图片提交；预先缓存四种选中状态并复用 PNG。该模式仍有图片通道成本，因此默认使用原生字符菜单。

天气页的原生文字通过文字容器创建及更新；地图、图标以及 0.1.23 的 1px 分隔线图片仍逐张提交。没有可核实的图片批量原子提交接口，不用并行发送图片来假装整帧刷新；真正的体验改善应通过真机测量确认。

## 验证与真机观察

0.1.23：用户确认相同亮度下 1px 原生分割线仍不可见、2px 可见，说明不能再通过降低原生容器的短边来可靠获取 1px 分割线。公开 SDK 仅提供整个矩形的边框宽度/颜色/圆角，没有单独的直线或单边边框控制。改为只将这些分隔线写入 Gray8 图像，每条线仅占一行/列像素，值为 136（8×17），保持原始起止位置。普通大小的图片容器承载细线，不依赖 1px 宽/高的原生容器，也不使用会产生半像素覆盖的 Canvas stroke。Information 的标题图标与左半横线共用一张图片，右半横线使用一张 226×20 图片；天气详情把两条竖线的上段与风向图标合并，下段与横线分在左右两张图片；环境页上段与月相图合并。所有页面最多 4 张图片，避免回到整屏文字位图；代价是 Information 从 1 张增至 2 张、天气详情及环境从 2 张增至 4 张，切页可能增加传输等待。文字、标题、外框保持原生；最终可见性仍需用户真机确认。此前把 1px 不可见解释为亮度问题不足以解决该反馈，本版更换实际绘制路径。

0.1.22 将首页选项切换从 0.1.20 的通用防连翻逻辑中分离。首页不再等待 550ms 操作间隔、350ms 静默期或上一次页面提交，仅过滤 100ms 内同方向的重复事件，反方向立即接受；选中状态同步变化，共享渲染任务合并在途更新，仍只更新原生标记列与概要。天气循环翻页与其他详情页保持原防连翻保护，不因修复首页响应而恢复一次手势跳过多页。实际桥接传输仍需耗时，未据此承诺真机固定响应毫秒数。

0.1.21 按用户反馈将 Information 和天气分割线恢复为 1px，保留 0.1.20 的 `borderColor: 8`；1px 线条的实际可见性仍需真机确认。去掉原生分页圆点及旧图片渲染中的分页方点。腾出的文字容器用于固定标题（x=59、y=23、486×27、`isEventCapture: 0`），原生外框手势容器内容改为空白，不再把标题放在会接收滚动的容器内。文字/图片数量与图片传输面积不增加。天气索引用模运算在四页间双向循环；第一页面上滑和最后页面下滑均不退出，双击继续返回首页，滑动重复事件过滤保持不变。

0.1.20 针对真机看不到分割线的反馈，取消短边只有 1px 的退化边框矩形，Information 横线和天气横竖线统一至少 2px 厚，`borderWidth: 1`、`borderColor: 8`，仍通过原生容器绘制。右上角四点改用官方字库中的 `●` / `○`；两者原生字宽均为 20px，放在 x=461、y=23、80×27 的同一文字容器中，避免大小不同的 `•` / `·` 加比例空格造成间距跳动。没有新增图片传输。输入层将连续滑动事件视作一段手势：忽略距上一条事件不足 350ms 的重复事件，接受的操作间隔至少 550ms，并在本次导航提交期间忽略重复事件；忽略时仍更新最后事件时间，持续滑动不会在固定节流时间一到就再次翻页。首个事件不等待防抖定时器，双击不经过滑动锁。该版本完成构建后仍需真机确认边框显示及手势体验，未将模拟器表现作为硬件结论。

- `node scripts/check-hud-rendering.mjs`：独立 PNG 解码、16 级灰度、容器大小、布局覆盖、无图片矩形重叠。
- `node scripts/check-hud-transport.mjs`：模拟慢速传输，验证原生菜单滑动发送和编码零张图片、图标与标签共用文字更新、备用模式一张完整菜单图片、PNG 缓存、刷新合并、过时图块取消和图片串行。
- `node scripts/check-home-navigation.mjs` 和 `node scripts/check-details.mjs`：输入、选中亮度、双击息屏唤醒、聊天滚动和迟到回复隔离。
- `npm run build`：TypeScript 与生产构建。
- `node scripts/check-weather-native.mjs`：天气四页在空数据、极端数值及摄氏/华氏下的 SDK 容器上限、原生细线及无自动换行约束。

本地官方模拟器曾检查主界面、AI、待办与 Information 页面。0.1.17 起 Information 只发送一张 20×20 标题图标，分隔线是原生文字。天气页按视图更新原生文字与地图、预报符号或月相图片；可从界面和 `HUD image transport` 日志核对每页的图块数量。

原生字符菜单已在全新模拟器会话核对四个图标和标题列。连续滑动五次的增量日志显示图片刷新 0 次、错误 0 条；慢速桥接回归检查同时验证图片编码 0 次。这证明选项切换已脱离图片通道，不代表实测硬件显示帧率。

控制台每个有图片发送的刷新输出 `HUD image transport`，字段有 `layout`、`images`、`imagePixels`、`pngBytes`、`encodeMs`、`sendMs` 和 `superseded`。`sendMs` 是等待桥接调用完成的耗时，不是眼镜逐像素可见的测量。

真机对比应在同一手机、同一眼镜和连接状态下检查进入 AI、进入待办、切换首页选项、连续翻天气页的响应。当前检查未测量实际 BLE 吞吐、左右眼刷新完成时间或显示 FPS。
